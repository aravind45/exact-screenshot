# DE-111 Professional Court-Form Preview Design

Date: 2026-03-18
Status: Approved for planning
Scope: DE-111 only, phase 1

## Summary

The current DE-111 preview is not showing the original California Judicial Council form. It is showing the structured fallback PDF generated by the CA form service. That fallback is useful for internal review, but it does not look professional enough to present to end users as a petition preview.

Phase 1 should replace that experience with an exact court-form preview and download flow for DE-111 based on the official PDF template. The preview and the download should be generated from the same rendering path so users see exactly what they will download.

## Problem

Today the DE-111 flow can generate three materially different outcomes:

1. A template-based filled PDF when a usable template is available.
2. A structured fallback PDF when the template cannot be filled.
3. A legacy generator path through the older document service.

This creates two user-facing problems:

1. The preview can look like an internal draft instead of a court filing.
2. The UI does not clearly distinguish between an exact court-form render and a fallback draft.

The repo confirms this behavior:

- The DE-111 fallback builder lives in `server/services/caFormService.ts`.
- The CA generator explicitly falls back to a structured builder when it cannot use a template.
- The Probate Petition page still presents the output as a normal "Petition Preview".

## Goals

- Show the original DE-111 PDF as the user-facing preview.
- Use one rendering pipeline for preview and download.
- Fill DE-111 using deterministic field placement, not a free-form draft layout.
- Make failure states explicit when exact-form rendering is unavailable.
- Keep the solution reusable for later rollout to DE-160 and DE-310.

## Non-Goals

- Solving all California forms in this phase.
- Solving all states in this phase.
- Building a model-training or large annotation workflow.
- Replacing estate extraction logic in this phase.

## Chosen Approach

Use coordinate-based overlay rendering on the original DE-111 PDF as the primary and expected path.

This is the recommended approach because:

- The current registry already supports coordinate placement and PDF field names.
- The local DE-111 template does not expose usable AcroForm fields through the current `pdf-lib` path.
- One-time form calibration is much lower risk than introducing a new PDF engine before user experience improves.

## Why Not Large-Scale Form Annotation

The current problem is not primarily an extraction-model problem. The issue is that the system is unable to produce a professional exact-form render for DE-111 and therefore falls back to a plain structured draft.

For this phase, "annotation" should mean:

- mapping each DE-111 field to exact page and coordinates
- documenting checkbox placement
- documenting formatting rules and computed behavior

It should not mean:

- labeling hundreds of examples
- training a model to learn PDF layout
- annotating screenshots of completed forms

## Rendering Pipeline

Phase 1 should standardize the DE-111 path as follows:

1. Resolve estate data plus per-request overrides into canonical DE-111 values.
2. Validate that the DE-111 exact-form prerequisites are present.
3. Load the official DE-111 PDF template.
4. Render all text and checkboxes onto the original form using calibrated coordinates.
5. Return the exact same generated bytes for preview and download.

The preview and the download must come from the same code path. The user should never preview an approximation and then download a different-looking form.

## Template Strategy

DE-111 should be treated as an overlay-first form.

The system should:

- continue attempting PDF field fill when a usable field is present
- rely on coordinate overlays as the normal DE-111 rendering method
- stop treating the plain structured fallback as the default preview experience

The current template should be reviewed as part of implementation because the local `DE-111.pdf` variants currently do not expose usable form fields through the existing `pdf-lib` inspection path.

## DE-111 Calibration Model

The DE-111 registry should become the source of truth for court-form placement.

Each DE-111 field entry should capture:

- canonical field key
- source type and source path
- text or checkbox type
- page number
- x/y coordinate
- font size and style where needed
- transform rules such as uppercase, date, currency, or phone formatting
- optional max-width or multiline behavior where the form is tight

The registry should also include DE-111-specific computed logic such as:

- petition type and authority boxes
- bond logic
- will and codicil logic
- estate value calculations where needed

## UX Changes

The DE-111 page should change its user-facing language and behavior:

- Rename `Preview Draft` to `Preview Court Form`.
- Only show the original filled DE-111 PDF in the preview modal.
- If exact rendering is unavailable, show an explicit error state instead of silently showing the structured fallback as a normal petition preview.

Recommended fallback UX:

- primary message: "We couldn't render the official court form right now."
- actions:
  - `Download blank DE-111`
  - `View internal draft summary` only if the product still wants to keep the structured fallback for support or debugging

## Readiness Rules

Exact-form preview should be blocked when legal inputs are missing or jurisdiction is incompatible.

Phase 1 should at minimum validate:

- California state context for DE-111
- decedent name
- date of death
- petitioner identity
- probate county
- core petition type logic
- publication and codicil inputs where applicable

This prevents weak-looking or legally inconsistent previews from being presented as ready court forms.

## Fallback Policy

The structured DE-111 fallback may remain in code temporarily, but it should not be the primary user-facing preview.

Recommended policy:

- exact-form render available: preview and download exact form
- required inputs missing: block and explain what is missing
- rendering infrastructure failure: show explicit error and blank-form option
- internal structured fallback: optional support/debug path only

## Implementation Areas

This design is expected to touch:

- `server/services/caFormRegistry.ts`
- `server/services/caFormService.ts`
- `server/routes/formRoutes.ts`
- `server/routes/documentRoutes.ts`
- `src/pages/ProbatePetition.tsx`

Possible implementation support scripts may also be needed for DE-111 coordinate calibration and PDF inspection.

## Verification

Phase 1 should be considered done only when all of the following are true:

- DE-111 preview uses the original court-form PDF base.
- DE-111 download uses the same rendering path as preview.
- The happy path does not use the structured fallback builder.
- Missing or incompatible inputs block preview with a clear explanation.
- Regression coverage exists for preview/download exact-form behavior and failure handling.

Recommended verification:

- targeted service tests for DE-111 field resolution and template rendering
- route tests for preview/download behavior
- UI test for the DE-111 preview button state and error messaging
- manual visual spot-check on known DE-111 scenarios

## Rollout

Rollout should happen in two steps:

1. Ship exact-form DE-111 preview and download.
2. Reuse the same template-calibration pattern for DE-160 and DE-310.

This keeps the initial change small while proving the exact-form rendering pattern on the most visible petition flow first.

## Open Decisions For Implementation Plan

- Whether to keep the internal structured fallback accessible anywhere in the product.
- Whether to fail closed when the official template cannot be rendered, or allow a clearly labeled internal draft fallback in limited contexts.
- Whether to create a dedicated DE-111 calibration helper script as part of the initial implementation.

## Recommendation

Proceed with a DE-111-first implementation that makes exact court-form rendering the standard for both preview and download, and demotes the structured fallback to a clearly labeled internal-only path.
